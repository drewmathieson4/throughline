# Decisions

One entry per non-obvious choice: what we picked, what we passed on, and why. Newest at the bottom.

## 2026-10-20 — Cloudflare Workers instead of a rented server
A Worker is a function Cloudflare runs on demand near the user and then shuts down; there is no machine to provision or patch, and the free tier covers a demo. We passed on a VPS or Vercel-plus-database because both mean a second vendor and a monthly bill. The trade is no long-running background jobs inside the Worker, which this app does not need.

## 2026-10-20 — React + Vite over Next.js
Cloudflare's own template wires React, Vite, TypeScript and the Worker into one `npm run dev` and one `wrangler deploy`. Next.js is the more recognizable name but needs an adapter on Cloudflare and brings server-rendering machinery this app does not use. The audience for this project cares about the workflow and the AI design more than the framework.

## 2026-10-20 — Hono for the API
Hono is a small, typed router built for the Workers runtime. The alternative was hand-written `if (url.pathname === ...)` branches in the Worker, which is fine for one route and unpleasant for fifteen.

## 2026-10-20 — D1 (hosted SQLite) over Postgres
D1 sits next to the Worker, needs no connection string or extra account, and is free at this scale. Postgres earns its keep with many concurrent writers or advanced features; a single-teacher notes app with a few hundred rows has neither.

## 2026-10-20 — Drizzle ORM with generated migrations
Tables are described once in TypeScript (`worker/db/schema.ts`); Drizzle types every query from that file and drizzle-kit turns schema changes into numbered SQL files under `drizzle/`. We never edit the live database by hand. A fresh clone rebuilds the database from the migration history.

## 2026-10-20 — Synthetic demo data only
Real student notes are FERPA-covered and re-identifiable even with names swapped. The hosted demo runs on a generated class and says so on screen. Real data, if ever used, stays on the teacher's own instance.

## 2026-10-20 — Opus 5.5 for synthesis and drafts, Haiku 5.5 for note tagging
Synthesis and prose quality are the product; the cost difference is cents per student. Tagging a note with the students it mentions is a bulk extraction task where the cheap model is plenty.

## 2026-10-20 — No tool-generated first commit
The scaffold was run with `--no-git` so the first commit is written by a person and says why the project exists.

## 2026-10-22 — Route tests run against a real D1 via wrangler's getPlatformProxy
`worker/routes/notes.test.ts` asks wrangler (already a devDependency) for the same Miniflare-backed `env` the dev server uses, with `persist: false` so each run starts from an empty in-memory database, then applies the committed migrations and the dev seed. Tests call the Hono app directly with `app.request(path, init, env)`. We passed on `@cloudflare/vitest-pool-workers`, which runs tests inside workerd itself, because it only supports Vitest 4 and the project is on 5; and on mocking the database, because a mock would not prove the SQL or the schema. The trade is that route code runs in Node during tests rather than workerd, which matters only if a route starts using a Workers-only API.

## 2026-10-22 — Demo data is a SQL file under scripts/, run by wrangler
`scripts/seed-dev.sql` holds one synthetic class and eight invented students with fixed ids and `INSERT OR IGNORE`, so `npm run db:seed:local` is safe to rerun and the route tests can load the same file. It lives outside `drizzle/` because wrangler treats every `.sql` in the migrations directory as a migration. We passed on a TypeScript seed script (needs a runner and a way to reach D1 from Node for the same result) and on a `/api/dev/seed` route (ships seeding logic in the Worker and needs guarding against production).

## 2026-10-22 — Whisper on Workers AI for voice-note transcription
The Anthropic API does not accept audio, so transcription needs a second model. Cloudflare's hosted Whisper (`@cf/openai/whisper-large-v3-turbo`) is reached through an `AI` binding on the Worker: no new package, no second vendor account, a free daily allowance and roughly a tenth of a cent per audio minute after that. We passed on the browser's Web Speech API (Chrome-only, routes audio through Google, stops on pauses, poor with names) and on the OpenAI Whisper API (same model but another key and vendor). The trade is that `npm run dev` reaches the real Cloudflare account for transcription, so the machine must have run `npx wrangler login` once.

## 2026-10-22 — Voice notes keep the transcript only; the audio is discarded
The recording is sent to Whisper and never written anywhere on the server. That removes an R2 bucket, a size-and-ownership check on stored keys, and cleanup of abandoned uploads, and it means no audio of a teacher talking about students sits in storage. `notes.audio_key` stays in the schema, null for now, so storing audio later is a feature change rather than a migration. Amended 2026-10-24 by offline notes: the audio now waits on the teacher's device, in the browser's IndexedDB, until the server has the note, and is deleted from there as soon as it does (or refuses it). With no signal that can be hours. It is the same device that recorded it, and the alternative is losing the recording.

## 2026-10-22 — A voice note is saved as soon as transcription finishes
No review-and-edit step before the note is written. Speed for the teacher wins; flagging a shaky transcript and correcting names and tags is planned as its own feature. Recording stops itself at five minutes and the page says so, so a long brain dump becomes several short notes, each one a separate Whisper call and a small unit for tagging.

## 2026-10-22 — Note bodies cap at 50,000 characters, text and voice alike
One server-side limit for both kinds. It is a backstop against runaway input, not a product constraint: nothing a teacher types comes close, and a five-minute clip transcribes to roughly 5,000 characters. D1 stores rows that size without trouble. The real cost of a huge note is the synthesis prompt it later joins, which stays small at single-teacher scale. Voice notes used to have no transcript limit at all; a 10 MB audio file uploaded straight to the API could have produced a 30,000-character note.

## 2026-10-22 — Route tests fake the AI binding
`getPlatformProxy` runs with `remoteBindings: false` and each voice test passes `{ ...env, AI: fake }`, where the fake returns a canned transcript or throws. The tests prove the route (type and size checks, empty-transcript rejection, what reaches Whisper, what is written) without network, cost, or a real model, which they could not prove anyway.
## 2026-10-22 — A student who leaves is marked, not deleted
`students.left_at` holds the date a student left the class; the active roster is `WHERE left_at IS NULL`. Deleting the row would cascade through `note_students` and strip the student from every note that mentioned them, destroying evidence the teacher may still need (a mid-year report, a transfer summary). A date beats a status enum because it answers "when" for free and costs the same null check. Reactivating is clearing the date, which covers the student who switches back. The roster endpoint returns everyone, departed or not; at a few dozen rows the client can hide them with a filter instead of a second request and a race guard around the toggle.

## 2026-10-22 — View switching in React state, no router
The app has a few views (notes, students, with roster import next) behind one class picker. A router package would add a dependency, URL design, and a second place where state lives, for no user-visible gain at this size. The selected class id is remembered in `localStorage` so a reload lands on the same class. Revisit if deep links to a student become a real need.


## 2026-10-22 — Tagging returns roster names, not ids, through a structured-output enum
The tagger (Haiku 5.5) answers in a fixed JSON shape whose `student` field is an enum of the roster's display names, built per request. The model cannot invent a student or mistype an id; the Worker maps names back to ids and drops anything unmatched. We passed on free-text answers parsed with regex (fragile) and on asking for ids (opaque strings the model copies badly). The trade is that two students with the same full name need a suffix on the label, which `rosterLabels()` adds.

## 2026-10-22 — Verified verbatim quotes, not summaries, as per-student evidence
Each tag stores the exact passages of the note about that student. Every quote the model returns is located in the note body (case and whitespace tolerant) before it is stored; a quote that is not there is dropped. We passed on model-written summaries because they are an interpretation, not evidence, and cannot be checked. The throughline synthesis will cite these quotes, so they have to be real.

## 2026-10-22 — Unresolved names live in their own table and are shown to the teacher
When a name fits more than one student ("Alex" with two Alexes enrolled) the tagger does not guess. The name, its quotes, and the candidate ids go in `note_mentions`; the notes page shows it; assign or dismiss endpoints close it. We passed on tagging every candidate as a suggestion (noise in the wrong student's throughline) and on dropping the mention silently (the teacher never learns a note went unfiled). Only open mentions are stored; closing one deletes the row.

## 2026-10-22 — Nicknames are a JSON array column on students
`students.aliases` holds the other names a teacher uses ("Juni"). A join table would be the textbook answer, but at a dozen students with a nickname or two each, a JSON text column that Drizzle parses is simpler to read, seed, and send to the tagger. Editing aliases through the UI is a later feature; the seed sets them for now.

## 2026-10-22 — Tagging runs inside the create request
`POST /api/notes` saves the note, calls the tagger, and returns the note with its suggestions, adding a few seconds. The note is saved before the call, so a failed call (no key, rate limit, refusal) costs nothing but the tags, and `POST /api/notes/:id/retag` tries again. We passed on a background job because the Worker has none (see the Cloudflare entry) and on a fire-and-forget `waitUntil` because the page would then have to poll for tags.

## 2026-10-22 — Eval cases are generated by Opus, reviewed by hand, and committed
`scripts/eval/cases.json` holds about 150 teacher notes with answer keys across 14 categories, written by Opus 5.5 from a brief per category and the tagger's own rules, then reviewed by a person. The file is committed so every run scores the same set and a prompt change can be compared against the last run. We passed on template-filled cases (exact answers for free, but unnatural text that never trips the model) and on hand-writing all of them (too few to catch rare failures). `npm run eval:tagging` fails below 90% precision or recall on tags. The first runs settled the model's effort setting too: `low` matched or beat `medium` on every category (99.7% precision, 100% recall on tags after three prompt tweaks) while being a fifth faster, so it is the default.

## 2026-10-22 — Notes are captured without a class; tagging infers it
The teacher just writes or speaks. The tagger looks across every class the teacher has, and the note's class is set from the students it finds when they all share one, or from a class the note names as a whole ("Period 3 was rowdy"); otherwise the note stays unassigned, and a name that fits students in two classes becomes an open mention that shows both with their class. Rationale: one less decision per note, and a batch of voice notes recorded in one sitting can span several classes. Suggestions set the class, not only confirmations, because most names are unique and waiting for a review step would leave every note unassigned until review tools exist; a teacher's confirm, add, or assign also settles it. We passed on a class dropdown next to the note box (one more tap per note, and wrong when a note spans classes), on an inbox page for unassigned notes (more UI than a label on the list), and on a manual class/student picker (deferred until there is evidence of how often inference fails). `notes.class_id` is nullable; a class given explicitly on create is kept. The migration rebuilds the `notes` table (SQLite cannot drop NOT NULL in place); D1 runs each migration inside a transaction, where `PRAGMA foreign_keys=OFF` is ignored, so the rebuild's DROP cascades through `note_students` and `note_mentions`. Harmless today because no production note has tags yet, but any future rebuild of a parent table needs a copy-and-restore step for its children first.

## 2026-10-22 — Roster import: the browser splits the file into cells, the Worker finds the students
The teacher picks a roster file or pastes names; papaparse turns the text into a grid of cells in the browser, and `POST /api/students/import` receives that grid as JSON. No file reaches the Worker, so there is no upload handling and the request is validated like any other. Everything that interprets the grid lives in `worker/roster.ts`, one pure module with one set of tests, because the model fallback below can only run server-side and the matching must use the same name cleaning the add-student form uses. We passed on parsing in the Worker (papaparse is UMD and the Workers bundle is the riskier place for it) and on a hand-written parser (quoted commas and embedded newlines are exactly where those go wrong).

## 2026-10-22 — The table is searched for, not assumed to start at row 1
A real export wraps the roster in metadata: a block of settings above, a summary below, blank lines between. Every row that names a name column ("Name", "First", "Surname"…) is tried as the header, the rows under it are read as students, and the candidate whose rows are most nearly all names wins; a "Students, 8" line in the settings block reads a few titles under it as names and far more non-names, so the real header beats it. A table ends at a row narrower than the header with nothing in the name columns. Cells with digits or symbols ("Grade 7 - A", "n/a") are never names, which is what keeps metadata out of the roster.

## 2026-10-22 — Column mapping: header rules, then content rules, then Haiku; no form for the teacher
Exports disagree about everything: "First Name" / "Given" / "Forename", a single "Student" column in either order, no header at all, ids and emails in between. Deterministic rules read the header row, then the shape of the data (a column of "Last, First" cells is unmistakable). Only when they give up (no header and two bare word columns, titles in another language) is Haiku 5.5 shown the first six rows and asked for a mapping. There is no preview or column-picking step: the teacher asked for the file to be imported, the summary says what happened, and a wrong guess is fixed on the students page (rename, mark as left, add by hand), which is cheaper than confirming every import. Without an API key, or when the model fails, the import says it found no names. We passed on model-first (a paid, non-deterministic call for every import when a header row answers most of them) and on a preview with per-column dropdowns (built, then cut: it asked the teacher to do the reading the import exists to do).

## 2026-10-22 — A section column creates or matches classes
When the file names two or more classes (a "Section", "Class", "Period" or "Homeroom" column), students go to classes with those names, matched to existing ones case-insensitively and created otherwise. One class name, or none, means the file is the roster of the class on screen, whatever the file calls it. Names already enrolled in their class are skipped, so importing the same file twice adds nobody and creates nothing. Inserts go in chunks of 16 rows inside one `db.batch()`, classes first: D1 allows 100 bound parameters per statement and a student row binds six; the batch is one transaction, so a failure part-way adds nobody.

## 2026-10-22 — Imported full names keep a first and a last name only
"Pell, Rowan James" and "Rowan James Pell" both become Rowan Pell: middle names are dropped, "Jr."/"III" stripped, surname particles ("de la Cruz", "van Beethoven") kept with the surname, and a name in ALL CAPS title-cased while mixed case ("McBride") is left alone. The tagger matches on first and last and a teacher says "Rowan", not "Rowan James"; a name that came out wrong is edited on the student page. A "Preferred name" or "Goes by" column becomes an alias, which the tagger already reads, so "Juni" in a note finds Juniper from day one.

## 2026-10-22 — A "last note" date per student, coloured by staleness
The roster shows when each student was last written about, with a dot: green within a week, amber within a month, red beyond that or never. The point is to be scannable at the end of a week: the red rows are the students the teacher has not noticed lately, which is the quiet failure mode this app exists to catch. The date comes from the newest note tagged to the student whether the tag is a suggestion or confirmed, because a suggestion still means a note named them; `noteCount` stays confirmed-only because it answers a different question (how much vetted evidence a report can draw on). The bands are computed in the browser from the current time, so the colour is right without a refetch. We passed on making the thresholds configurable (no evidence yet that a teacher wants different ones) and on sorting the table by staleness (the dot is enough to find the reds in a class of thirty).

## 2026-10-22 — The notes list filters by class and student in the browser
Two selects above the list narrow it to one class, one student, or both. The filtering happens in the browser: the page already loads every note and every roster (hundreds of rows for one teacher), so a query parameter would add a round trip per click for nothing. A student's filter matches notes where they are tagged, suggested or confirmed, and also notes where they are a candidate for a name the tagger could not settle, so filtering by Alex Marsh shows the bare-"Alex" notes with their "unsure who" line instead of hiding them. We passed on server-side filtering (revisit if a teacher ever has thousands of notes) and on a search box (names are a dropdown away; free-text search is a different feature).

## 2026-10-22 — Demo notes are written by Opus with answer keys and loaded through the API
`scripts/demo/notes.json` holds a term of synthetic notes (about 45 per class, dated 1 Sept onward) written by Opus 5.5 one class at a time: it plans an arc per student first, then writes the notes in date order so each student's notes tell a story the later synthesis can find. Each note carries an answer key in the eval's format, and `npm run demo:load` posts the notes to a running server one by one so the real tagger tags them, then prints where the tagger and the key disagree. The roster is read from the API, not from a second file, so the notes always match the database. We passed on a SQL dump of pre-tagged notes (it would not exercise the tagger and would go stale on every prompt change), on reusing the eval cases as the demo (they are deliberately adversarial and undated, so they read like a test suite), and on regenerating the eval roster from the seed (the 180 answer keys depend on its class membership; the two rosters are independent on purpose). The file is committed and read by a person before loading, like the eval cases.

## 2026-10-23 — No confirmed flag: a resolved tag is live, ambiguity is a mention the teacher settles
`note_students.confirmed` is gone: a tag the tagger resolves to one student is a tag from the moment it is written, and the only thing put in front of the teacher is a name the tagger could not settle, which was already an open mention with candidates. The eval supports trusting resolved tags: 99.7% precision overall and 100% on the lookalike, transcript, shared-first-name, and alias categories, and when unsure the tagger produces a mention, not a guess. This supersedes the "noteCount stays confirmed-only" rule in the last-note entry above. The trade: nothing records whether a tag came from the model or the teacher, so retag is only allowed on a note with no tags and no mentions (the state a failed tagging call leaves) and refuses a tagged note; re-running the tagger over everything is the demo loader's job. We passed on a per-tag confidence score from the model (not calibrated, so a threshold would be a guess, and the eval already measures what a score would estimate) and on a "source" column in place of the flag (no feature needs it yet).

## 2026-10-23 — A document of student reports becomes one note per student, cut by Haiku and verified verbatim
A progress report, report-card comments, or any write-up about students, imported through a class's Add menu (`POST /api/documents`; see the sorting entry dated 2026-10-24), becomes one note of kind `progress_report` per student of the picked classes the document is about. The splitter sees only those classes' roster: the teacher has said who the file is about, and a first name shared with a student in another class cannot make a name unsure. The body is the passages about that student, copied from the document and checked to exist in it (same `quoteLocator` rule as tags), the note is tagged to them with those passages as quotes, and `notes.source_name` records the file. A name that fits two students becomes an unassigned note with an open mention, so the existing "unsure who" UI settles it. We passed on one note per document tagged to everyone in it (a thirty-student report pack would be one 40,000-character note whose quotes are the real content, and every student's throughline would cite the same note) and on free-text splitting without verification (the evidence has to be real). `worker/documents.ts` shares the roster enum, mention resolution, and quote checking with the note tagger through `resolveMentions`/`mentionEntry` in `worker/tagging.ts`; only the prompt differs (whole sections, not sentences; a document date). The trade is that a document about one student is copied back almost whole, so a long file is a slow call: the cap is 60,000 characters, about fifteen pages.

## 2026-10-23 — Document text comes from Workers AI toMarkdown; the file is never stored
PDF and Word files are converted on the same `AI` binding Whisper uses (`env.AI.toMarkdown`), which handles .pdf, .docx, .xlsx and .csv, is free for those formats, and needs no package. Embedded images are not converted (that part runs an image model and is billed). Plain text and Markdown are decoded in the Worker. We passed on pdf.js and mammoth in the browser (two packages, two parsers to keep working) and on sending the PDF to Claude directly (it can read PDFs, but the text is needed anyway to verify the passages it returns). Like audio, the uploaded bytes are read once and discarded; only the text that became notes is kept. Same caveat as transcription: `npm run dev` reaches the real Cloudflare account, and route tests fake the binding.

## 2026-10-23 — A document's notes are dated from the document, else the file, else now
Haiku reads a stated date (a date line, a letterhead date) and the Worker checks it is a real day between 2000 and today; the browser sends the file's modified time as the fallback. A stated date is stored at noon UTC so it shows as that day in any time zone. No date field on the upload: the teacher drops the file and the notes land where they belong on the timeline, and a wrong date is edited later like any note's. We passed on asking for a date per upload (one more step, usually answerable from the document itself).

## 2026-10-23 — A failed split writes nothing
Unlike a note, which is saved before tagging because its body is useful on its own, a document only has value once it is cut into per-student notes, and a stored copy of a twenty-page report with no tags would be noise. So a missing key, a model failure, or an unreadable file is a 502 or 400 and the teacher tries again or pastes the text as a note. A document sorted as both kinds is different: its course material is worth keeping on its own, so a failed split stores the material, leaves the notes the file made before alone, and says the students could not be read.

## 2026-10-23 — Importing the same document again replaces what it made before in those classes
Notes remember the file they came from (`source_name`) and materials keep its name, so a second import of `report.pdf` into Period 3 deletes what the first made there and writes the new set in the same transaction: its `progress_report` notes in the class, its notes for names it could not settle (those have no class, and count as Period 3's when one of the candidates is in it), and its course material. The page says how many notes were replaced. It is one rule for both kinds, so the result card's switch to the other kind removes what the wrong guess made. A re-import is almost always a correction (the roster was fixed, a name was added, the syllabus was revised) or a double drop, and either way two copies would double every student's evidence or leave the synthesis two syllabuses to choose between. Classes the teacher did not pick keep theirs. We passed on refusing the second import (the teacher would be stuck) and on keeping both (silent duplication). The trade is that tags the teacher settled on the first set go with it, and that two different files with the same name in one class replace each other.

## 2026-10-23 — Course materials are a table of their own, listed on a Class tab
A syllabus, unit plan or grading policy is about the course, not a student, and has no date worth sorting by, so it does not become a note: `class_materials` holds one row per imported file per class, and a Materials tab beside Students lists them. We passed on storing them as class-level notes (a ten-page syllabus in the notes list is noise, and the 50,000-character note cap is the wrong limit) and on a per-class settings form (the `settings` table stays for report rules and style samples, which belong to the report-draft feature). They arrive through the same import as a document of reports (see the sorting entry dated 2026-10-24), stored once for each picked class, so a syllabus two sections share is read and summarised once.

## 2026-10-23 — Haiku reads the course structure out of a material; the raw text is kept too
On upload the text goes to Haiku once, which returns a fixed shape: a one-line description, goals, grading categories with percentage weights, units with timing, and policies. That is what the page shows, what the grade summary will weight by, and what the synthesis can cite as the course's own aims. The raw text is stored beside it because the extraction is lossy and the synthesis prompt may want the wording. We passed on asking the teacher to type the weights (the document already says them) and on raw text only (then nothing could use the weights without a second model call at read time). Weights outside 0–100 and blank lines are dropped in the Worker; the model is told to leave a list empty rather than guess.

## 2026-10-23 — A failed summary still stores the material
Without a key, or when the model fails, the file is stored with `summary` null and the page says so, unlike a document of reports, which is not worth keeping uncut. Importing the same file again replaces the copy in each picked class (see the re-import entry above), so a revised syllabus does not leave the synthesis two copies to choose between; this replaces the earlier rule of storing it twice.

## 2026-10-23 — Grade books: two shapes, read by rules; Haiku only names categories
`POST /api/grades/import` takes the same grid of cells the roster import does, so a CSV export, a TSV, or cells pasted from a spreadsheet all work and no file reaches the Worker. `worker/gradebook.ts` reads two shapes. Wide is what every grade book exports: a row per student, a column per assignment, often a points row and a due-date row under the header, plus columns to ignore (email, id, "Overall Grade") and summary rows ("Class average"). Long is a row per score with student, assignment and score columns and perhaps max, category and date. Score cells may be `17`, `17/20` or `85%`. Blank or "Missing" is missing work, and "Excused" or "N/A" makes no entry. Anything else, like a letter grade, is reported as a skipped cell. When the file has no points possible, the max is read from `x/y` cells, else 100, else the column's top score, and the summary names those columns. The model's only job is the category of a title the rules cannot place ("Fertile Crescent Map"). It gets one call per import with the list of titles and the category names, and never a score or a student's name. Without a key, or on failure, those titles are "other". When the class has a syllabus with weights, its category names are the categories ("Quiz 3" files under "Quizzes"), so the weights line up. We passed on model-first parsing (a grade book is regular enough for rules, and it would mean sending every score to the API) and on a column-mapping form (same reason as the roster: the summary says what happened). `.xlsx` is not read yet; CSV export is one click in every grade book.

## 2026-10-23 — Re-importing a grade book updates scores in place and keeps what the new file lacks
`grade_entries` has a unique index on (student, assignment), and the import upserts on it. A grade book is exported again and again through a term, so the second import of the same file changes nothing and a corrected score replaces the old one. An entry absent from a later file is kept, because exports often cover one grading period or one category. The trade is that a renamed assignment becomes a second row; there is no delete-a-grade UI yet. `position`, the assignment's order in the file, is stored so the timeline works when the export has no dates.

## 2026-10-23 — Grade import never creates students
Rows are matched to the class roster on first and last name, then on a nickname and last name, cleaned the same way the roster import cleans them. Unmatched rows are skipped and listed, and the summary says to import the roster first. A grade book is the wrong place to learn who is in a class: it often carries students who dropped, test accounts and typos, and a misspelt name would create a duplicate student with half the scores.

## 2026-10-23 — The grade summary is computed in code, and missing work is counted, not averaged
`worker/grades.ts` turns a student's entries into the numbers the student page shows and the synthesis will cite. The overall is weighted by the syllabus when the newest material that states weights covers every category the student has a score in. Otherwise it is a plain mean and the page does not claim the weighting. A newer material without weights, such as a unit plan, does not switch weighting off. Per-category means name a strongest and weakest category when at least two categories have two scores each. The trend compares the first half of the timeline with the second and needs four scores, with five points either way to be rising or slipping. A teacher can read "72% in the first half, 84% in the second", which a regression slope does not give them. The biggest win and loss are the scores furthest from the student's own mean, at least ten points away, shown with the class mean on that assignment so a test everyone found hard is not read as the student's slump. Missing work is left out of every mean and reported as a count. Counting it as zero would guess at the teacher's late-work policy, and the demo syllabus accepts late work for a week. The trade is that the overall can read higher than the official grade book. We passed on asking the model for the analysis: these numbers have to be the same every time they are computed.

## 2026-10-23 — The synthesis organises the evidence; the teacher writes the report
The Reports tab gives each student a structured summary, not a draft. It opens with a 200–300 word narrative of the period (where the student started, what changed, where they are now) so the teacher has the story before the detail. Then come highlights the teacher can tell as anecdotes, strengths, areas to grow, change over the period, progress on each syllabus goal, and gaps. A report in the teacher's own words is the point of a narrative report, and a model-written draft would take that away. The narrative is a briefing, not report prose, and the teacher still writes the report; `report_drafts` stays unused for now. Each point's sources show as chips under it (folded behind a "3 sources" toggle at first; the UI redesign opened them, so checking a claim is one tap), and a point resting on one source is marked. ## 2026-10-23 — Opus sees each student's verified quotes, not whole notes; class notes are context it cannot cite

## 2026-10-23 — Citations are an enum of evidence ids, and what they cite is copied into the summary
Every note, grade and the grade summary gets an id (N1, G1, GRADES), and every citation field in the output schema is an enum of this student's ids, so the model cannot cite something that is not there. ## 2026-10-23 — A summary belongs to a date range and is reused until its evidence changes

## 2026-10-24 — Every text and voice note goes through an on-device queue
Teachers record in classrooms with bad signal, so a capture must never depend on the connection. Each note is written to IndexedDB first (`src/offline/store.ts`) and then sent; with no connection the save finishes at once ("Saved. Uploads when you're back online"), and the Record screen and the feed show "N notes waiting to upload". The queue (`src/offline/queue.ts`, pure and unit-tested with the storage and the send passed in) flushes on start-up, on the browser's `online` event, when the app comes back to the foreground (an installed app resumes without reloading), and after each save, oldest note first. A fetch that never reaches the server ends the flush and keeps everything; a 5xx, 401, 408 or 429 keeps that note and moves on to the next; any other 4xx is about the note itself (nothing was heard), so it is dropped and a toast gives the server's reason. `ApiError` in `src/api.ts` carries the status so the queue can tell a refusal from a dropped connection. Each send gives up after 60 seconds, since one bar of signal can hang a request for minutes, and a send that did arrive is safe to repeat (next entry). Uploaded notes join the list in `notedAt` order rather than on top. The shell no longer waits for `/api/classes` when offline, so Notes opens with no connection. We passed on localStorage (strings only and a few MB, so no audio), on Background Sync (Chrome only; iOS has none), and on a library such as Workbox or idb for about a hundred lines of code. The report gap's "Record answer" stays online-only, since it tags the new note to the student straight away and needs its id back.

## 2026-10-24 — A hand-written service worker so the app opens offline
`public/sw.js` is copied unhashed to `/sw.js` and registered from `src/main.tsx` in production builds only (in dev, Vite's unbundled modules would be served stale). On install it caches the icons, the manifest, the app shell (`/`, which is `index.html`; Cloudflare redirects `/index.html` there, and a redirected response cannot answer a page load) and the hashed scripts, styles and fonts the shell names, so the first reload with no signal works. ## 2026-10-27 — Sign in with Google, hand-rolled, with sessions in D1
Teachers sign in with a Google account; every `/api` route except `/api/health` and `/api/auth/*` needs the session cookie, and a signed-out browser sees only the sign-in screen. The OAuth authorization-code flow is written out in `worker/google.ts` and `worker/routes/auth.ts`: send the browser to Google with a random `state` kept in a short-lived HttpOnly cookie, swap the returned code for a token, read the profile, and refuse a callback whose state the app did not set or whose email Google has not verified. Hono's own `hono/cookie` handles the cookies, so there is no new package. We passed on `arctic` (it covers only the three HTTP calls; the state check, the cookie rules, the hashed token and the ownership checks are ours to write either way) and on `better-auth` (it would own part of the schema and hide a flow that is sixty lines). Sessions are rows in D1 (`sessions`): the cookie carries a random token, the row holds its SHA-256, so a copy of the database holds no usable sessions, and deleting the row signs that browser out. The cookie is HttpOnly, `SameSite=Lax` (Strict would drop it on the redirect back from Google), `Secure` except on plain-http localhost, and lasts 30 days. Signing out deletes the row and clears the cookie. The browser asks `/api/auth/me` on load; a 401 from any call shows the sign-in screen, and a request that never got an answer opens the app anyway so a note can still go into the offline queue. `run_worker_first: ["/api/*"]` in `wrangler.jsonc` is what lets a page navigation to the callback reach the Worker instead of the SPA's `index.html`.

We reversed the earlier call because the teacher's voice is already in the evidence: the quoted notes are theirs, and a draft that reuses them in their phrasing is closer to what they would write than a blank box is, and editing a sound draft is faster than writing from a brief. The report is written by Opus from the saved evidence JSON (`worker/report-model.ts`), never from the raw notes: every claim in the summary has already passed the citation check, and the model sees prose, quotes and numbers, no note or evidence ids. The thin areas the summary names are passed as "do not write about these". A report belongs to one synthesis row (`reports.synthesis_id`): regenerate the evidence and there is no report until one is written again, and the roster says so (`reportId` null). Every write is a new row and the newest is shown, so "Write again" keeps nothing from the old one. Generated and edited text are separate columns: the edit saves itself shortly after the last keystroke and on blur, "Reset to generated" sets it null for nothing, and the gap between the two is measurable later. Copy puts the text on the clipboard; there is no export, since every school's report system is a paste box.

## 2026-11-10 — Hard deletes for students, classes and accounts, and a JSON export
Colleagues who put their own students in need a way to take them out again, so each level has a delete and the account has an export. `DELETE /api/students/:id` is a hard delete: the row goes and the foreign keys cascade through the student's tags, grades, evidence summaries and reports. The notes stay, since a note is the teacher's and one left with no tags already means class context. It does not replace "Mark as left" (2026-10-22): leaving keeps the evidence, deleting is for a student who should not be in the app at all, and the confirm says so. `DELETE /api/classes/:id` is one row delete too: its students and theirs, every note with that `class_id` (with tags and mentions), materials and settings cascade; a note with no class that was tagged to one of its students survives untagged, because notes hang off the owner, not the class. `DELETE /api/auth/account` reuses the demo purge (`deleteUsers` in `worker/demo.ts`, once `deleteDemoUsers`): notes, then classes, then the user in one batch, which is the order the two foreign keys without a cascade (`owner_id` on both) need, and it already worked for a demo visitor, so nothing is special-cased. The cookie is cleared with the answer, as sign-out does. Every delete is final: no soft-delete column, as with notes (2026-11-09); Cloudflare's point-in-time copy of the database (30 days) is the only way back, and only Drew can run it. Each delete confirms in a Panel; only the account asks the teacher to type their email, because nothing is bigger and it is the one slip the app cannot partly recover from.

`GET /api/auth/export` returns everything the account owns as one JSON document: classes with their settings, students and grades, and materials; notes with their tags' quotes and open mentions; the evidence summaries; the reports. It is built from the same owner-scoped selects the routes use, so it holds exactly what the teacher can see. The answer carries `Content-Disposition: attachment` with a dated file name, so the menu item is a plain link and the browser does the download; same-origin navigation sends the session cookie, and no fetch-and-blob code is needed. One request, at a teacher's scale, rather than a job and a file store the Worker has no scheduler for.

The teacher's rules live per class in the `settings` table that had waited for this: a target length, phrases to keep out, a note to the writer, and pasted examples of their own past comments for the voice, edited in a panel off the Report tab that saves as typed. They reach the prompt inside data tags with the instruction to match the voice and never the facts; the model is told that nothing inside the tags overrides the system prompt. Spend and caps follow the 2026-10-27 rules: `modelAccess()` meters the call, a demo visitor over their four gets a 403, a failed write refunds through `reserved()`.

## 2026-11-10 — Real student data for allowlisted colleagues
